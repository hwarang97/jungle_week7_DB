# B+ Tree 정렬 Phase 검증 퀴즈 — 답안

---

## Part 1. 개념 확인

### A1.
실제 데이터(레코드 포인터)는 **리프 노드에만** 저장된다.
내부 노드에는 **키(key)만** 저장되며, 자식 노드로 안내하는 "이정표" 역할을 한다.

### A2.
리프 노드끼리 **링크드 리스트**로 연결되어 있다.
이유: **범위 검색**(WHERE id BETWEEN 10 AND 50)을 할 때, 시작 리프를 찾은 뒤 링크를 따라가면 되므로 트리를 다시 탐색할 필요가 없다.
없으면 범위 검색 시 매 키마다 루트부터 다시 탐색해야 한다.

### A3.
시간복잡도: **O(log n)**

100만 개, order 100일 경우:
- 각 노드가 최대 99개 키를 가짐
- log₁₀₀(1,000,000) ≈ 3
- 최대 **3~4번** 노드 방문으로 검색 가능

### A4.
B Tree는 모든 노드에 데이터를 저장하지만, B+ Tree는 **리프 노드에만 데이터를 저장하고 리프끼리 연결**되어 있다.

## Part 2. 손으로 그리기

### A5.

order = 3이면 각 노드에 최대 2개의 키가 들어감 (order - 1).
3개가 되면 분할 발생.

**(1) 1 삽입**
```
[1]
```

**(2) 2 삽입**
```
[1, 2]
```

**(3) 3 삽입 → 분할 발생**
리프에 [1, 2, 3]이 되므로 분할.
중간값 2를 기준으로 분할.

```
    [2]
   /   \
 [1]  [2, 3]
```
※ B+ Tree이므로 리프에 2가 남아있음 (B Tree와의 차이)
※ 리프끼리 연결: [1] → [2, 3]

**(4) 4 삽입**
4는 루트의 2보다 크므로 오른쪽 리프로.
[2, 3]에 4 추가 → [2, 3, 4] → 분할 발생.
중간값 3을 부모로 올림.

```
    [2, 3]
   /  |   \
 [1] [2] [3, 4]
```
※ 리프 연결: [1] → [2] → [3, 4]

**(5) 5 삽입**
5는 3보다 크므로 오른쪽 리프 [3, 4]로.
[3, 4, 5] → 분할 발생.
중간값 4를 부모로 올리려 하는데, 부모 [2, 3]에 4 추가하면 [2, 3, 4] → 부모도 분할.

루트 분할:
```
       [3]
      /   \
   [2]    [4]
   / \    / \
 [1] [2] [3] [4, 5]
```
※ 리프 연결: [1] → [2] → [3] → [4, 5]
※ 트리 높이가 2에서 3으로 증가

(참고: order=3 B+ Tree의 분할 규칙 구현에 따라 약간 다를 수 있음.
핵심은 "리프가 꽉 차면 분할하고 중간 키를 부모로 올린다"는 원리를 이해하는 것)

### A6.
Q5 완성 트리에서 키 3 검색:

1. 루트 [3] 방문 → 3 == 3이므로 오른쪽 자식으로 (또는 같으면 오른쪽 규칙에 따라)
   - 실제로는 구현에 따라 "key ≤ 3이면 왼쪽" 또는 "key < 3이면 왼쪽"이 달라짐
   - 일반적: key < 3? No → 오른쪽 자식 [4]로
2. 내부 노드 [4] 방문 → 3 < 4이므로 왼쪽 자식으로
3. 리프 [3] 도착 → 키 3 발견, 값 반환

경로: **루트[3] → 내부[4] → 리프[3]** (3번 노드 방문)

### A7.
키 6 삽입:
- 루트[3] → 6 ≥ 3 → 오른쪽 → 내부[4] → 6 ≥ 4 → 오른쪽 → 리프[4, 5]
- [4, 5]에 6 추가 → [4, 5, 6] → 분할 발생
- 중간값 5를 부모 [4]에 올림 → [4, 5]
- [4, 5]는 아직 2개이므로 부모 분할 없음

```
         [3]
        /   \
     [2]    [4, 5]
     / \    / |  \
   [1] [2] [3] [4] [5, 6]
```
※ 리프 연결: [1] → [2] → [3] → [4] → [5, 6]

## Part 3. SQL 연동 사고

### A8.

```sql
INSERT INTO users VALUES (1, 'jiun', 25);
```
→ **B+ Tree 사용 O**: 레코드를 테이블에 저장한 뒤, id=1을 B+ Tree에 인덱스로 등록 (bptree_insert 호출)

```sql
SELECT * FROM users WHERE id = 3;
```
→ **B+ Tree 사용 O**: id는 B+ Tree 인덱스가 걸려있으므로, bptree_search(3)으로 해당 레코드 위치를 O(log n)에 찾음

```sql
SELECT * FROM users WHERE name = 'sein';
```
→ **B+ Tree 사용 X**: name 필드에는 인덱스가 없으므로, 전체 레코드를 처음부터 끝까지 **선형 탐색** (O(n))

### A9.
- "INSERT 처리 함수의 **레코드를 테이블에 저장한 직후** 시점"
  → 레코드 저장 → 부여된 id로 bptree_insert(tree, id, record_pointer) 호출

- "SELECT 처리 함수의 **WHERE 조건을 확인하는** 시점"
  → WHERE 절이 id 조건인지 판별 → id면 bptree_search 호출, 아니면 선형 탐색

## Part 4. 의사코드 읽기

### A10.

**(A)**: `order - 1` (또는 "최대 키 개수", "MAX_KEYS")
→ 리프 노드가 가질 수 있는 최대 키 개수. 이보다 작으면 그냥 삽입.

**(B)**: `leaf를 분할하여 new_leaf를 생성` (split_leaf)
→ 키가 꽉 찼으므로 노드를 반으로 나눔. 앞 절반은 기존 leaf, 뒷 절반은 new_leaf.

**(C)**: `부모 노드에 new_key와 new_leaf 포인터를 삽입` (insert_into_parent)
→ 분할로 새로 생긴 리프를 부모가 가리키도록 키를 올림. 부모도 꽉 차면 재귀적으로 분할.

### A11.

**(D)**: `리프 노드가 아닌 동안` (is_internal / is_not_leaf)
→ 리프에 도달할 때까지 내부 노드를 따라 내려감.

**(E)**: `node.children[i]` (i번째 자식 포인터)
→ key보다 큰 첫 번째 키의 왼쪽 자식으로 내려감. key가 모든 키보다 크면 마지막 자식으로.
